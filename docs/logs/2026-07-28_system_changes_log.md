# Honeypot Pipeline Setup & Fixes (Documentation)
**Date:** July 13-15, 2026

This document summarizes the configurations, fixes, and optimizations applied to the Honeypot Data Pipeline to ensure stability, correctness, and performance.

## 1. Service Setup (Systemd)
*   **Processor Agent:** Created and started `/etc/systemd/system/honeypot-processor.service`.
*   **Collector Agent:** Created and started `/etc/systemd/system/honeypot-collector.service`.
*   **Environment Config:** Centralized all sensitive variables (MongoDB URI, ZeroTier Configs, Redis) into `/etc/honeypot-agent.env` with `600` permissions (root-only access).

## 2. ZeroTier Interface Update
*   **Issue:** Zeek and Go Agent were listening to an old ZeroTier interface (`zttqhz5xog`).
*   **Fix:**
    *   Updated Zeek's `/usr/local/zeek/etc/node.cfg` to use the new interface `ztxoocdlsi`.
    *   Updated `/etc/honeypot-agent.env` with `SENSOR_ZT_IFACE="ztxoocdlsi"` and `SENSOR_ZT_IP="10.58.33.42"`.
    *   Updated `ALLOW_CIDRS` to include the new subnet `10.58.33.0/24`.

## 3. Firewall (UFW) Ports
*   **Issue:** The system had a strict default `DENY` policy for outbound traffic, which blocked connections to MongoDB Atlas and general HTTP traffic.
*   **Fix:** Added UFW rules to allow outbound traffic for port `27017` (MongoDB) and port `80` (HTTP).
    *   `sudo ufw allow out 27017/tcp`
    *   `sudo ufw allow out 80/tcp`

## 4. Redis Memory Management (MaxLen)
*   **Issue:** `collector-agent` and `processor-agent` were pushing data to Redis Streams (`XADD`) infinitely without trimming, which could cause a Memory Leak / OOM on the Raspberry Pi.
*   **Fix:** Edited Go code to include `MaxLen: 5000` and `Approx: true` in all `XADD` commands. Recompiled both agents.

## 5. Cowrie Data Missing Bug Fix
*   **Issue:** The `collector-agent` had a logical bug in `shouldKeepCowrie` that filtered out and dropped all Cowrie events if the attacker's IP was not from the LAN or ZeroTier subnet.
*   **Fix:** Modified `shouldKeepCowrie` in `collector-agent/main.go` to accept all Cowrie events regardless of the source IP. Added `READ_FROM_START="true"` to `.env` to recover all historical data. Recompiled and restarted the agent.

## 6. Zeek BPF Filter (CPU Optimization)
*   **Issue:** Zeek was capturing and analyzing its own backend traffic (MongoDB and Redis), which wasted CPU resources.
*   **Fix:** Appended a BPF filter to `/usr/local/zeek/share/zeek/site/local.zeek` to completely ignore ports `27017` and `6379`.
    ```zeek
    # Ignore MongoDB (27017) and Redis (6379) to save CPU
    redef capture_filters += {
        ["ignore-mongo-redis"] = "not port 27017 and not port 6379"
    };
    ```
    Deployed the changes via `zeekctl deploy`.

## 7. Git Setup & SSH Firewall Fix
* **Issue:** `git push` was failing with SSH timeouts because outbound port 22 was blocked by UFW.
* **Fix:** 
  * Opened UFW outbound for port `22` (`sudo ufw allow out 22/tcp`).
  * Renamed remote typo (`orgin` -> `origin`) and successfully synced the Monorepo to GitHub.

## 8. Data Architecture Clarifications
* **Unified Schema:** Confirmed `processor-agent` correctly outputs both `cowrie` and `zeek` objects in every MongoDB document. This "Unified Schema" approach prevents `undefined` frontend crashes in the upcoming Next.js Dashboard.
* **Timezone Issue:** Clarified that MongoDB stores time in UTC, ensuring developers account for the UTC+7 offset when querying local time events.

## 9. Threat Intel Automation & Zero-Trust Isolation
* **Issue:** Static Threat Intel (JA3, HASSH) files become outdated. However, enabling outbound network access for the Honeypot to download updates breaks strict isolation principles.
* **Fix:**
  * Created `/home/cpe27/honeypot-pipeline/lookups/update_threat_intel.sh` to fetch latest signatures from GitHub and automatically restart the processor.
  * Added a weekly Cron job (`0 0 * * 0`) running as `root` on the Host OS to perform this update securely outside the honeypot sandbox.
  * **Strict Isolation:** Added an `iptables` rule to completely drop ALL outbound packets generated by the `cowrie` user:
    `sudo iptables -I OUTPUT 1 -m owner --uid-owner cowrie -j DROP`
    This traps any hacker trying to download malware from inside the Cowrie shell, even if they escape the Python environment to a bash shell.
  * Saved the rule persistently via `iptables-persistent`.
