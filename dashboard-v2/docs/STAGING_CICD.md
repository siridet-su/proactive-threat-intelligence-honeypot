# dashboard-v2 team staging

This repository now has a staging-only delivery path:

```text
feature/* -> pull request -> CI only
staging   -> CI -> exact tested artifact -> staging VM :3001
main/release -> existing separately approved production process
```

The workflow is `.github/workflows/dashboard-v2-staging.yml`. It runs only for
dashboard/staging deployment files and the focused dashboard contract test.
Backend or research-only changes do not deploy the frontend.

## CI and artifact identity

CI runs the commands the dashboard currently supports:

```bash
npm ci --legacy-peer-deps --ignore-scripts
npm run lint
npx tsc --noEmit --pretty false
python -m pytest -q tests/test_dashboard_v2_api_integration_contract.py tests/test_dashboard_v2_staging_contract.py
npm run build
node scripts/package-staging.mjs
```

The peer-dependency option is required by the existing React 19 and
`react-simple-maps` dependency resolution. The build uses Next standalone
output. The package contains the generated `server.js`, traced `node_modules`,
`.next` (including copied static assets), `public`, `package.json`, and a
non-secret `build-metadata.json`.

The manifest binds the archive to the full Git commit SHA, Git tree SHA,
`package-lock.json` SHA-256, GitHub Actions run ID, and archive SHA-256. The
deploy wrapper rechecks all of those values before switching the staging
pointer. It never rebuilds from a mutable checkout.

## Staging runtime boundary

The intended VM layout is:

```text
/opt/honeypot-dashboard-v2-staging/
  releases/<commit>-<artifact-sha-prefix>/
  current -> releases/<release>
  bin/deploy-staging
  shared/last-deployment.json
```

`honeypot-dashboard-v2-staging.service` runs as the existing non-root
`honeypot` user and starts the standalone server on `127.0.0.1:3001`. Its
protected environment file is
`/etc/honeypot/services/dashboard-v2-staging.env`. It uses the verified
loopback monitor origin `http://127.0.0.1:8090` and has separate staging
dashboard credentials generated by `bootstrap-staging-runtime.sh`.

The production unit, pointer, port, environment file, backend workers, and
Mongo configuration are outside this namespace. The service unit does not
grant a frontend write path. The BFF catch-all accepts authenticated `GET` and
`HEAD`; its upstream request method is fixed to `GET`. `POST`, `PUT`, `PATCH`,
and `DELETE` on the catch-all return `405`. `/api/auth` remains a separate
cookie-only `POST`/`DELETE` route so application authentication is not weakened.

The root-owned wrapper validates archive paths, rejects overwrites, switches
`current` atomically, restarts only the staging service, checks the loopback
listener, checks the staging marker/build ID, checks unauthenticated API
access fails closed, and restores the previous staging pointer if health
fails. It keeps at most five validated staging release directories and never
removes the active release.

## GitHub Environment setup

A repository administrator must create the `staging` Environment and add only
these deployment secrets:

```text
STAGING_SSH_HOST
STAGING_SSH_PORT
STAGING_SSH_USER
STAGING_SSH_PRIVATE_KEY
STAGING_SSH_KNOWN_HOSTS
```

The private key must belong to the dedicated non-root
`dashboard-staging-deploy` account, and `STAGING_SSH_KNOWN_HOSTS` must be a
verified pinned host-key entry. The workflow rejects empty/malformed values
and uses `StrictHostKeyChecking=yes`; it never runs `ssh-keyscan` and never
uses `StrictHostKeyChecking=no`.

The deployment job can access those secrets only on a trusted push to the
`staging` branch. Pull requests, including fork pull requests, run CI without
deployment secrets. The staging deploy account may invoke only the root-owned
`deploy-staging` wrapper through the exact sudo rule installed by
`setup-deploy-identity.sh`; it cannot restart production or backend services,
read Mongo credentials, or obtain an unrestricted root shell.

## Local validation

From the repository root, after dependencies are available:

```bash
cd dashboard-v2
npm ci --legacy-peer-deps --ignore-scripts
NEXT_PUBLIC_DASHBOARD_DEPLOYMENT_LABEL=STAGING \
NEXT_PUBLIC_DASHBOARD_BUILD_ID="$(git -C .. rev-parse HEAD)" \
npm run build
node scripts/package-staging.mjs
```

The local command creates its archive under the system temporary directory
unless `STAGING_ARTIFACT_DIR` is set. It does not contact the VM or Cloudflare.

## Cloudflare handoff

Cloudflare is intentionally not configured by the repository workflow. The
target is a remotely managed tunnel whose published application route points
only to `http://127.0.0.1:3001`. A human with the Cloudflare account must
confirm an active zone, create/select a tunnel, install the official
`cloudflared` package, store the tunnel-specific token in protected VM
configuration, and create a Cloudflare Access self-hosted application for the
exact staging hostname. The Access Allow policy must include only the approved
team email addresses (or a deliberately approved team domain); it must not
include `Everyone`, all valid emails, or unrestricted OTP. Application auth
remains required behind Access.
